RUNBOOK: Emergency Node Failover Protocol
Trigger: Node unresponsive, hardware fault confirmed, or cascading failure risk
Severity: Always CRITICAL — execute without delay

Step 1: Confirm node is truly failed — check 3 consecutive metric reads with zero or null values
Step 2: Identify best failover target using priority order:
  - Same customer tier node with util below 70%
  - Same customer tier node with util below 85%
  - Cross-tier node with explicit customer approval
  - Queue requests if no viable target exists
Step 3: Redirect DNS or load balancer to failover target within 90 seconds
Step 4: Notify customer SLA owner immediately — do not wait for RCA
Step 5: Begin hardware diagnosis on failed node in parallel with traffic restoration
Step 6: If hardware fault confirmed, initiate replacement SLA with infrastructure team
Step 7: Document full timeline: first anomaly signal, failover initiation, traffic restored
Step 8: Do not restore traffic to repaired node without 15-minute burn-in validation
Recovery: Full incident report delivered to customer within 2 hours of resolution
